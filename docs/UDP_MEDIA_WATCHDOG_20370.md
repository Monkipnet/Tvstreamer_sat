# TVStreammerSAT5 203.70 — проверка реальных медиаданных на UDP-CBR

**Исходный материал:** полный архив 203.69, без изменения пользовательской конфигурации.
**Статус:** исходники + патч; локальные unit/static tests пройдены. Полная сборка
TVStreammerSAT5 с GStreamer и испытания на реальном HTTP/SRT → UDP пока не проводились.
Не устанавливать непосредственно на рабочий 43-канальный сервер без одноканального
испытания на тестовой системе. Обновление основного бинарника требует перезапуска службы.

## Почему появилась 203.70

Журнал ШансонТВ 23.09: в 14:49:10 зафиксировано `result=media-restored`,
в 14:49:16 — UDP PCR lock. Воспроизведение на UDP, по сообщению пользователя,
оставалось зависшим до ручного перезапуска отдельной плитки в 14:53:49.
`media-restored` прежнего сетевого watchdog фиксировал только возврат *входа*;
обнаружение PCR и заполнение стартового буфера не подтверждают последующее
поступление новых кадров до настоящей UDP-отправки.

## Изменения

1. `StableUdpOutput::sendDatagram` после успешного `sendto` анализирует ровно
   переданный TS datagram: считает пакеты с известными выходными PID аудио/видео,
   старты видео-PES с читаемым PTS и изменения PTS. PID `0x1FFF`, PAT/PMT и PCR
   не дают ложного продвижения медиа. Показанный в интерфейсе битрейт CBR на
   решение не влияет. Счётчики привязаны к одному UDP-sender и одному поколению
   пайплайна, сохраняя `shared_ptr` для безопасного завершения старого sender.
2. Существующий монитор одного канала сверяет новые доставленные через `sendto`
   медиапакеты и PTS с *реальным входным* медиапрогрессом. Если входные медиа
   продолжают поступать, но после 20 секунд старта нет ни одного реального
   UDP-медиапакета либо уже начавшиеся медиапакеты перестали идти на 18 секунд,
   выполняется полная перестройка **только этого канала**. Когда видеотаймстампы
   на входе продолжают меняться, отсутствие прогресса читаемых UDP PTS 18 секунд
   либо постоянный PTS после 3+ PES стартов запускает такое же восстановление.
3. Защита: 20 секунд на старт/начальный резервуар, минимум 60 секунд между
   восстановительными действиями нового watchdog; при потере *самого входа*
   действует уже имеющийся сетевой watchdog, а не принудительные циклы UDP.
   Дополнительные UDP-CBR выходы имеют независимые счётчики.
4. Для контролируемых каналов Telegram-сообщение об окончательном возврате
   основного источника откладывается до наблюдения новых медиаданных на UDP
   в течение нескольких секунд, и при наличии входного видеопрогресса требует
   продвижения выходного PTS. Даже после этого сообщение формулируется как
   **«Основной источник: новые медиаданные передаются на UDP»**, а не как
   гарантия декодирования телевизором. Если инструментированный UDP-выход
   отсутствует, отправляется предупреждение о неподтверждённом выходе.
5. Диагностика `UDP MEDIA WATCH 203.70` включает точный UDP endpoint,
   причину, число реальных доставленных медиапакетов и PTS advance,
   число успешно отправленных датаграмм и задержку прогресса.

## Область действия и ограничения

* Для нового UDP watchdog: вход HTTP MPEG-TS или SRT, UDP-CBR выход,
  `remapEnabled=true`, `transcodeEnabled=false`, известный выходной PID
  (для ШансонТВ: V-PID 258, A-PID 257). Прежние механизмы контроля остальных
  каналов сохраняются.
* Подтверждение `sendto()` означает передачу датаграммы ядру, а не получение
  её на другом устройстве и не успешное декодирование там. Не выявляются
  ошибки коммутатора, IGMP/multicast, потери после отправки, повреждённые
  PAT/PMT/CC или замороженная картинка при исправно меняющихся PTS.
* Видео-PES PTS, который не помещается в первом TS-пакете или зашифрован,
  не анализируется; в этом случае остаётся контроль медиапакетов. Не используется
  ложная эвристика «большая доля NULL = авария».
* HTTP-ошибки источника `Server does not support seeking` и
  `Internal data stream error` требуют отдельного исследования. Данный патч
  не переписывает `souphttpsrc` и не гарантирует устранения проблем источника.
* В существующем коде может быть запланирован перезапуск службы, если даже
  после попытки остановки одного канала старый пайплайн **не может** быть
  завершён. Новый watchdog сам службу не перезапускает; проверяйте журнал
  и описанный ранее механизм защиты от зависшего teardown при испытаниях.

## Проверки перед развёртыванием

В корне исходников 203.70:

```bash
node tests/test_media_watchdog_20369.js
node tests/test_udp_watchdog_20370.js
g++ -std=c++17 -O2 -Wall -Wextra -Werror \
  tests/test_ts_media_progress_20369.cpp -o /tmp/test_ts_media_progress_20369
/tmp/test_ts_media_progress_20369
g++ -std=c++17 -O2 -Wall -Wextra -Werror \
  tests/test_udp_media_delivery_20370.cpp -o /tmp/test_udp_media_delivery_20370
/tmp/test_udp_media_delivery_20370
cmake -S . -B build-media-20370 -DCMAKE_BUILD_TYPE=Release \
  -DTVSTREAMMERSAT5_BUILD_OSCAM_MINI=OFF
cmake --build build-media-20370 --parallel 2 --target TVStreammerSAT5
```

Для одноканального теста используйте отдельный экземпляр сервиса, не занимая
рабочие UDP/multicast порты. В тесте моделируйте три состояния: непрерывный
вход с NULL-only на выходе, вход с продвигающимся видео PTS при замершем выходе,
переход на резерв с возвращением основного источника. Мониторьте записи:

```bash
journalctl -u tvstreammersat5.service --since '30 minutes ago' --no-pager -l | \
  grep -E 'UDP MEDIA WATCH 203.70|PRIMARY RECOVERY 203.70|MEDIA WATCH 203.69|NETWORK INPUT RECOVERY'
```

При испытании проверяйте фактический UDP-приём на **другом хосте**, а не только
надпись «UDP media verified» в журнале. Без успешного одноканального испытания
не заменяйте работающий бинарник 203.69.
