Fix: false OVERLOAD RECOVERY loop after NETUP reservoir startup
---------------------------------------------------------------
Field diagnostics on stream-1788239497586 (SvetloeTV_BY_SD) proved a repeating
cycle after every UDP -> SRT pipeline rebuild:

  * UDP input was already active (typically ~420-456 kB/sample window),
  * output_bytes was still 0 while NETUP 203.53 intentionally filled its
    1500 ms startup reservoir,
  * the 1-second overload watchdog interpreted this normal startup condition as
    outputStalled,
  * after two damaged windows it armed OVERLOAD RECOVERY,
  * once output became clean, the existing 15-second recovery gate rebuilt the
    pipeline again, restarting the same cycle.

This repeated rebuild loop also repeatedly destroyed/recreated SRT listener
branches and was observed immediately before the caller/eventpoll leak state.

203.60 adds a 4-second post-start/post-rebuild grace period ONLY to the
output-stall predicate of the existing overload watchdog.  During the grace:

  * input/output continuity-error detection remains active immediately;
  * severe CC damage remains active immediately;
  * only "active input + too little output" is ignored while the intentional
    NETUP startup reservoir is allowed to fill;
  * after 4 seconds the existing output-stall protection works unchanged.
