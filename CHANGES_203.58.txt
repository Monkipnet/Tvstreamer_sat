TVStreammerSAT5 203.58
=====================

Scope
-----
Per-stream HLS passthrough A/V offset correction for channels whose provider
carries a stable audio lead. No changes to the proven 203.57 transcoder cadence,
HLS scheduler, Provider-PCR clock, NETUP 203.53 reservoir pacer, continuity
normalization, PCR restamping or CBR sender timing.

Evidence for TV3Bel
-------------------
Direct provider capture (~105 s):
  A-V start = -1034.667 ms
  A-V end   = -1029.334 ms
  drift     = +5.333 ms

Clean SAT5 UDP capture from source 172.10.0.117 (~60 s):
  A-V start = -1082.667 ms
  A-V end   = -1096.000 ms
  drift     = -13.333 ms

Therefore the ~1.0-1.1 s video-after-audio offset is already present at the
provider and remains essentially constant; it is not an accumulating SAT5 rate
drift. A fixed audio timestamp delay is the appropriate correction.

Changes
-------
1. StreamConfig gains `audio_delay_ms` (0..5000 ms, default 0).
2. Web UI exposes Audio delay under HLS synchronization.
3. Stable UDP passthrough for segmented HLS can shift audio PES PTS/DTS forward
   by the configured delay. The transport packets are not buffered or reordered.
4. The correction is intentionally disabled for transcoded streams and for
   non-HLS input. A valid configured A-PID is required.
5. New runtime marker:
     HLS A/V sync 203.58: ... audio_delay_ms=... mode=audio-pes-pts-dts-forward
6. UDP diagnostic stats include audio_delay_ms, audio_pts_shifted and
   audio_dts_shifted.

TV3Bel setting
--------------
Recommended initial value from the measured clean SAT5 output:
  audio_delay_ms = 1080

Expected after correction:
  existing A-V start -1082.667 ms + 1080 ms ~= -2.667 ms
  existing A-V end   -1096.000 ms + 1080 ms ~= -16.000 ms

Protected paths unchanged
-------------------------
- 203.57 shared transcoder: yadif fields=top + videorate + 25/1.
- 203.56/203.55 transcoded SRT/HTTP byte pacing.
- HLS scheduler LOW/TARGET/HIGH and 203.42 retry behavior.
- TV3 Provider PCR clock / 203.36 lock logic.
- SOUZ deadline shaper / 203.41 logic.
- NETUP 203.53 reservoir-monotonic-1316 output path.
- No QSV introduced.

Network note
------------
A separate network problem was confirmed on multicast 239.0.0.2:1234:
  172.10.0.117 -> 5.000 Mbit/s (TVStreammerSAT5)
  172.10.0.1   -> ~4.48 Mbit/s (second sender)
The second sender must still be removed or moved to another multicast endpoint;
203.58 does not attempt to solve multicast source collisions.
